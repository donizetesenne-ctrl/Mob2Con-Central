📋 Arquitetura do Modelo

Resumo ▾
O Analítico RG 2.0 MCP 2 é um modelo híbrido com DirectQuery via Analysis Services (Fabric) para todas as tabelas de fato e dimensões principais. Agrupa dados de 4 workspaces distintos do Power BI Service, mais uma tabela de import (Faturamento). O padrão é Star Schema com Composite Model — cada fonte AS representa um domínio de negócio independente.

🔴 Tabelas Duplicadas de Dimensão
dim_loja, dim_fornecedor, dim_rede e dim_visitante existem em versões "1" e "2" para contextos de fontes distintos (Projetos vs. PPU). Gera ambiguidade, duplica manutenção e pode causar resultados divergentes em análises cruzadas.
→ Criar dimensões compartilhadas via Shared Dataset ou consolidar em um único modelo semântico base.
🔴 Múltiplas Tabelas de Métricas (4 versões)
Métricas, Métricas 2, Métricas 3, Métricas 4 existem em paralelo, cada uma vinculada a uma fonte AS diferente. Isso fragmenta a experiência do desenvolvedor DAX e dificulta a criação de KPIs compostos.
→ Consolidar usando EXTERNALMEASURE com prefixo de namespace, ou criar um Metrics Table virtual centralizado.
🟠 Faturamento em Mode Import
A tabela Faturamento_Fornec_Geral_RG é a única em modo Import, enquanto todo o restante usa DirectQuery. Isso cria uma assimetria na estratégia de atualização e pode gerar dados defasados em análises financeiras.
→ Migrar para dataflow no Fabric ou DirectQuery via API.
🟠 Bases por Rede Isoladas (10 tabelas)
Cada rede (NORDESTAO, GBARBOSA etc.) tem sua própria tb_base_REDE. Qualquer adição de nova rede exige replicação de tabela no modelo. Não há consolidação automática.
→ Criar tabela unificada via UNION em M ou DAX; parametrizar a rede como dimensão.
🟠 Ausência de Página de Alerta / KPI Summary
Não há uma aba dedicada a alertas automáticos (estoque zerado, metas não atingidas, lojas críticas). Os dados para isso existem no modelo (Score Qualidade Dados, Flag Saúde Estoque), mas não são expostos de forma operacional.
→ Criar página "Alertas Diários" com visuais condicionais para envio via e-mail HTML.
🟠 Sem Dimensão de Tempo Unificada
Existem 3 tabelas de calendário: Date, dim_tempo e dCalendario, cada uma vinculada a uma fonte diferente. Impossibilita comparação temporal cross-source sem DAX específico.
→ Criar uma dimensão de data master compartilhada entre todos os fatos via Composite Model.
🟡 Sem Análise de Eficiência de Custo
Existem "Custo Saldo de Horas" e "Valor Ajustado" na tb_analitico_geral_unica, mas não há uma análise de ROI ou custo por visita/hora no relatório.
→ Criar medida ROI = Venda (R$) / Custo Saldo de Horas e expor na página Financeiro.
🟡 Página "Análise Ruptura Motivo" Pouco Dinâmica
A página tem apenas 1 card de medida (Produto Avariado) e 9 shapes/images — indica uso intenso de layouts estáticos/pré-montados, sem drilldown dinâmico.
→ Substituir shapes estáticos por visuais nativos com filtros por tipo de problema.
✅ Oportunidade — Relatório Diário por E-mail HTML
O modelo possui todas as métricas necessárias para um e-mail diário rico: KPIs de vendas, estoque, ruptura, promotor, captação. A tabela Atualização Power BI pode ser o gatilho de última atualização.
→ Conectar via Power Automate + DAX Query + template HTML Mob2Con para envio automatizado.
✅ Oportunidade — Score Composto de Saúde
Score Qualidade Dados e Flag Saúde Estoque já existem como medidas, mas não são combinados em um único índice de saúde operacional por fornecedor/rede.
→ Criar "Score de Saúde Operacional" = f(ruptura, estoque, visitas, horas) como KPI principal.
✅ Oportunidade — Detalhamento de Fornecedor por Tier
A tabela tb_analitico_geral_unica tem colunas Tier, FTE, Filtro ABGR que segmentam fornecedores, mas não há página dedicada a comparação entre tiers.
→ Criar página "Análise por Tier" com ranking e comparativo entre A/B/G/R.
Com base na análise completa do modelo, o Projeto de Envio Diário em HTML pode aproveitar diretamente as métricas, tabelas e estrutura existentes sem necessidade de alterações no modelo semântico.
